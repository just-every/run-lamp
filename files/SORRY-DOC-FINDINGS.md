# Sorry documented export/API census — 2026-11-17

Read-only, public documentation research; no provider account or customer data used. Source bodies retained only in this research directory, outside the publication packet. This authored census can be incorporated into the report.

## Export and envelope

- https://help.sorryapp.com/article/97-export-subscribers documents subscriber export via saved authenticated GET responses, each page saved separately, plus a support-requested export. Its current direct HTTP response says page=1&per_page=500, 500 default, advance page=2 etc. Search/open caches exposed an older February 2024 version; direct HTTP research fetched the current September 2026 text. No documented all-in-one export archive/schema found. Do not fabricate a Sorry ZIP or top-level combined JSON as the incumbent's format. A Lamp-owned capture manifest may index separate native responses, labeled as a transport wrapper.
- https://docs.sorryapp.com/v1 and https://docs.sorryapp.com/v1/error-response-codes specify HTTPS base https://api.sorryapp.com/v1/, authenticated API, JSON response envelope: {response:{...}} for single objects and {response:[...],count:N} for lists; pagination details may appear. Include supports dot nesting and comma-separated relations (e.g. brand,notices.updates). 10 requests/second/token and 429 are documented. Plan account-free fixture tests for 401/403/429/retry, no live request needed.

## Authenticated REST API shape

### Subscribers — https://docs.sorryapp.com/v1/subscribers
GET /pages/:page_id/subscribers; page and per_page, default 500. include=components; filter[for_component]=ID returns direct component followers plus all-component followers.
Named properties/GET example fields: id; email; phone_number; slack_webhook_url; microsoft_teams_url; notify_by_email; notify_by_phone_number; notify_by_slack_webhook_url; notify_by_legacy_slack_oauth_token; notify_by_microsoft_teams_url; notify_by_google_chat_space; first_name; last_name; nickname; company; tag_list; avatar_url; created_at; updated_at. component_ids is explicitly documented as a create input; components is documented as include, so test both documented request/response relation representations deliberately rather than asserting component_ids always appears on GET.
Docs forbid adding Slack, MS Teams or Google Chat subscriptions without subscribers authorising themselves. Retain channel intent/identity metadata safely, but do not convert old integration URLs/tokens into active Lamp grants. No verified/confirmed field is documented in the REST subscriber shape; fixtures must not invent confirmation as Sorry-supplied evidence. tag_list prose says comma-separated while examples use JSON arrays; support/report both. Example contains invalid email jane.doe@@acme.com, useful malformed-input case, not a valid normal subscriber.

### Components/services — https://docs.sorryapp.com/v1/components
GET /pages/:page_id/components. Named fields: id; state; name; description; position; parent_id; created_at; updated_at. parent_id is recursive nesting; state is notice-derived including ancestors/descendants. REST property table allows operational/degraded/partially-degraded, while public Status API uses operational/degraded/under-maintenance. Keep each source dialect explicit. No REST pagination limit declared on this page; use multi-response fixture only with documented general pagination metadata rather than inventing a default.

### Incident and maintenance notices — https://docs.sorryapp.com/v1/notices
GET /pages/:page_id/notices and /pages/:page_id/notices/:notice_id. include=components,updates; example uses page=1 but no REST notices page-size promise. Named fields: id; type; state; timeline_state; subject; synopsis; link; began_at; ended_at; created_at; updated_at; tag_list. Planned fields also: begins_at; ends_at; should_automate_schedule. Nested relation components and updates are supported by include; component_ids is documented create/update input.
Types: unplanned, planned; general is documented with an in-development note and shown in a response. Do not silently convert general notices into incidents or omit them.
Unplanned states: investigating, identified, recovering, resolved, false_alarm. Planned states: scheduled, cancelled, underway, complete. timeline_state: future, present, past_recent, past_distant; derived from source history-window policy.
Additional create/update-only inputs: initial_comment; additional_comment; should_publish; begins_at_date; begins_at_time; duration_in_minutes. Do not assert these are exported response fields if absent; test documented response forms first. Notice synopsis derives from first update and is not equivalent to latest body.

### Notice updates — https://docs.sorryapp.com/v1/notice-updates
GET /pages/:page_id/notices/:notice_id/updates. Named fields/properties/example: id; content; should_publish; link; created_at; updated_at. should_publish is documented as whether a historical update was sent externally, not proof of customer delivery and not permission to resend. REST properties do not document update state, unlike public Status API updates; preserve missing state honestly rather than fabricate historical transitions.

### Notice templates — https://docs.sorryapp.com/v1/notice-templates
GET /pages/:page_id/notice_templates; named fields: id; name; subject; initial_comment; component_id (optional collection-page scope); created_at; updated_at. Filter example returns content instead of initial_comment; handle/test both documented variants with a visible conflict if both disagree. Example pagination has current, previous, next, per_page, pages, count with per_page=25. component_id scopes a template to a collection page, not necessarily an affected-service list. Filter[name_cont] and filter[component_name_cont] documented. One summary endpoint typo says /notices/:notice_template_id, while detailed retrieval is /notice_templates/:notice_template_id; use detailed endpoint, record documentation inconsistency.

### Update templates — https://docs.sorryapp.com/v1/update-templates
GET /pages/:page_id/update_templates; named fields: id; name; content; component_id (optional collection-page scope); created_at; updated_at. List example also includes subject on one update template despite omitting it in property table; include in field accounting. Pagination: current, previous, next, per_page, pages, count; sample per_page=25. Same collection-page scope caveat. No general combined templates endpoint documented.

### Page settings — https://docs.sorryapp.com/v1/status-pages
GET /pages/:page_id. Named fields/properties/response: id; state; name; timezone; support_email; support_telephone; support_url; visible_to_search; meta_title; meta_description; google_analytics_id; timeline_threshold; timeline_threshold_in_days; timeline_sort_order; locale; created_at; updated_at; endpoint; send_notifications_by_email; send_notifications_by_sms; send_notifications_by_slack; send_notifications_by_microsoft_teams; send_notifications_by_twitter.
include relations: brand; components; custom_domain; notices; subscribers; theme. include is a query parameter, not a stored field. No theme-specific schema/endpoint was documented in the linked API navigation; a theme object can be retained as source metadata/unknown fields and reported, but do not claim invented theme keys are Sorry's documented format.

### Branding — https://docs.sorryapp.com/v1/branding
GET /pages/:page_id/brand. Named property/response union: color_state_ok; color_state_warning; color_state_info; color_state_alert; color_navbar_background; color_navbar_links; color_navbar_button_background; color_header_background; color_header_links; color_header_text; color_body_background; color_body_links; color_body_text; created_at; updated_at. color_state_info/color_state_alert appear in response but not property table; color_navbar_button_background appears in table but not response. Do not omit them from accounting. Logos/icons are mentioned in overview, but no logo/icon fields appear in this documented REST brand schema.

### Custom domain — https://docs.sorryapp.com/v1/custom-domain
GET /pages/:page_id/custom_domain. Response fields: type; from; to; created_at; updated_at. domain is a create input. Retain old source DNS details for review only; old provider CNAME target does not configure or verify Lamp DNS. Documented timestamp example here uses YYYY-MM-DD HH:MM:SS +0000, unlike the ISO examples elsewhere.

## Public Status API is a separate dialect

https://sorryapp.sorryapp.com/api documents account-free /api/v1/status, /api/v1/components, /api/v1/notices, /api/v1/notices/:id (on each status-page origin). Public dialect does not export subscribers or authenticated page settings/templates.
- /status: page.name, state, state_text, url, links.components.href/count, links.notices.href/count, created_at, updated_at.
- components: id,state,name,description,parent_id,metrics_summary,links.children.href/count,created_at,updated_at. metrics_summary fields: timeframe_start,timeframe_end,percentage_uptime.percent,percentage_uptime.words,url. Optional summary can be null.
- notices common: id,type,timeline_state,state (when applicable),subject,url,began_at,ended_at,created_at,updated_at,tag_list,links.self; unplanned impact_time.seconds/words; planned begins_at/ends_at. List latest_update has state/content/created_at/updated_at (general can omit state). Detail has components and updates, and updates may have state/content/created_at/updated_at without IDs.
- Public pagination is explicitly max 25 for component/notice collections and meta.count,total_count,next_page. next_page examples differ between /api/v1/... and /v1/...; do not follow arbitrary or cross-origin paths. Tests should cover supported normalization and refuse hostile links.
- Component state text has under-maintenance in current direct docs; older cached version uses under_maintenance. Preserve/test declared compatibility explicitly rather than assume one spelling everywhere.
- Component metrics endpoint is separate /api/v1/components/:id/metrics, with timeframe_start,timeframe_end,show_calculations params. Response includes component.id/name,timeframe_start/end,percentage_uptime.percent/words/calculation,mean_time_to_recovery.seconds/words/calculation,mean_time_between_failures.seconds/words/calculation,url,calculation_data_in_timeframe.total_time.seconds/words,total_impact_time.seconds/words,notices.href/count. These are historical provider-calculated metrics, not raw monitoring observations; if fixture includes these, classify exactly and do not turn them into Lamp's measured uptime.

## Fixture advice

Use separate files containing actual native response envelopes, with a Lamp-owned deterministic manifest of request URL, status, headers, response file, and source SHA. Generate >500 subscribers (501 or 1,003); >25 public components/notices and >25 each template kind. Cover all documented enum states, unknown fields, null/empty optional data, deeply nested parent chains, unicode names/comments, duplicate IDs, notices with multiple timestamped updates, collection-scoped templates, documented content-vs-initial_comment variant, and false notify flags. Keep malformed and hostile cases outside the good fixture so successful import counts are unambiguous. The authenticated REST docs do not promise a single combined export; all API response pages should remain distinguishable for completeness/pagination proof. No live account is necessary to build or prove these synthetic cases.
